# Castalia OS 0.2.0 — release notes

*Released 2026-08-22.*

The release that makes "install next to Windows" true on a normal computer,
gives a machine that will not boot somewhere to be repaired from, and builds
the 32-bit image the whole product is actually about.

## Before you upgrade

**If you are going to install alongside Windows, back it up first, and turn
off Fast Startup and hibernation in Windows** (`powercfg /h off` as
administrator, then shut Windows *down* rather than restarting). Castalia will
refuse to resize a Windows that was left hibernated — which is correct, and
means you cannot install until you fix it. See
[the dual-boot guide](../install/dual-boot.md).

## New

**Make room on a full disk.** `--mode shrink` takes space off an existing NTFS
or ext2/3/4 filesystem and installs into the gap it opens. Until now
"install alongside" only worked on a disk that already had unallocated space —
which almost no real computer has, so the friendly mode was the one almost
never offered. Verified on a real 24 GiB disk with a single edge-to-edge NTFS
partition and 6.5 GB of data in it, with a file placed deliberately out past
where the new boundary falls, checksummed either side.

**A recovery boot environment.** A "Recuperación" entry now sits in the boot
menu next to Safe Mode. It runs before the system starts, mounts your disk
itself, and offers five things: restore a point, check and repair the disk,
repair the boot menu, a shell, and reboot. It works *when the root filesystem
will not mount*, which is the case the whole feature exists for.

**The text installer can keep a Windows.** It offers the same three install
modes as the graphical one, shows what is already on the disk, prints what
will be kept and what will be lost, and sets a password. It could previously
only erase the whole disk — on machines that fall back to text mode precisely
because their graphics are broken, and which are *more* likely to be
dual-booting, not less.

**A hardware probe.** `castalia-hwprobe` reads what is in the machine out of
sysfs, matches it against a shipped quirks table, and records the result for
the Hardware Center. It runs at install time and on every boot. It claims
nothing it was not told: an unlisted machine gets `suspend: unknown`.

**32-bit ISOs, built and booted.** `live-i386` per commit and `classic32`
nightly, both booted under an emulated CPU that cannot execute 64-bit code.
Every ISO this project had ever built was amd64, on a product whose FLOOR
(§4.1, §16) is a Pentium 4.

**The documentation set.** All thirteen documents §20 asks for, and an offline
Help Center generated from them at package time — no JavaScript, no web fonts,
nothing fetched. `castalia-manual` opens it.

## Changed

**The §16.2 memory budgets were re-budgeted and signed off** (§16.5). They
were written before anyone measured what a Qt window costs, and the Control
Center's 25 MB budget turned out to be 84% of the cost of an empty window that
does nothing. The new numbers are the measured figures plus about 10%, and a
new *toolkit floor* row budgets the empty window itself — the row every other
memory number is built on top of. What it costs a user is about 24 MB of 512;
the full accounting is in §16.5.

## Fixed

**An alongside install wrote the wrong partitions into `/etc/fstab`.** It
named the neighbour's Windows partition as `/boot` and Castalia's swap as `/`.
The install looked fine right up to a first boot that either failed or mounted
somebody else's system partition read-write. Nothing caught it because the
loopback test checks that the other OS survives and that Castalia's files
landed — both true — and the fstab is only read at a boot that test never
performed.

**The installer raced `partprobe`.** `mkfs` could be issued while the kernel
was still rebuilding the partition device nodes, producing a failed install
that looks like a corrupt disk on a table that is, a second later, exactly
right.

**The §6.2 128 GiB rule crashed instead of refusing.** On a large disk the
installer would offer a mode and then raise a traceback on the last screen.
It is now a refusal with an explanation, and — counter-intuitively — a shrink
on a partition reaching past the 128 GiB mark must free *more* space, not
less, or `/boot` lands where a vintage BIOS cannot read it.

**A failed step printed a traceback instead of the reason.** `parted` and
`ntfsresize`'s own words now reach the screen.

## Known regressions

None known.

## Hardware

**QEMU and real block devices only.** No machine has completed §19.2's
real-hardware certification, and §23.7 #1 and #6 cannot be met until one has.
See [the hardware guide](../hardware/README.md) — including how to contribute
a result, which needs a machine rather than a maintainer.

What *is* verified on real storage: the plain install, the alongside install
and the NTFS shrink, each on a real block device with checksums before and
after.
